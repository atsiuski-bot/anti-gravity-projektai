### [timetracking] computeWorkerStats omits a finished plain task's own manualMinutes, undercounting totalHours/activeDays vs DailyStatistics and the CSV export

- **File:** `src/utils/workerStats.js`:141-161, 284-292  
- **Finder severity:** high  
- **Votes real:** 3/3

computeWorkerStats builds totalWorkMin (and totalHours/totalWorkMinutes/activeDays/avgPerDay/normCoverage/productivePct/avgDayLength/weekConsistency) EXCLUSIVELY from summing `raw.workSessions` durations into `days[date].workMin` (lines 142-149, 160). It never adds a plain (non-quickWork, non-systemTask, non-timeChanged) finished task's own `manualMinutes` — the additive, session-less worked time that `calculateCurrentTotalMinutes` treats as real (manualMinutes + timerMinutes) and that a legacy/manually-entered task carries with NO backing work_sessions row.

Both sibling implementations that consume the exact same `raw.tasks` array explicitly add this: `aggregateDaily` in src/utils/reportAggregate.js (lines 183-204, with the comment 'summing sessions alone made the downloaded payroll timesheet report FEWER hours than the same manager sees on screen') and `DailyStatistics.jsx`'s own on-screen total (`manualTasks`/`totalManualMinutes`/`totalWorkedMinutes`, lines 775-809), guarded by the identical isSystemTask/isQuickWork/timeChanged checks. workerStats.js has no equivalent addition anywhere in the function, and this is locked in by its own test fixture (src/utils/workerStats.test.js lines 21-26, 43: two plain tasks carry `manualMinutes: 100` and `manualMinutes: 90` and the test still asserts `s.totalHours === 14` i.e. exactly the 480+360 session minutes, silently dropping 190 minutes of task-level manual time).

Impact: computeWorkerStats is what Reports.jsx's on-screen 'Komandos suvestinė' / 'Mano suvestinė' cards (TeamPeriodSummary/PersonalPeriodSummary, via buildReport -> current.totalWorkMinutes) and the downloadable Markdown/JSON AI report's 'Viso dirbta' metric are built from. For any worker whose finished, non-quickwork/non-call task carries manualMinutes with no matching work_sessions row (the same legacy/manually-typed-time case the CSV and DailyStatistics guard was written for), these two on-screen/exported totals will show FEWER hours than DailyStatistics's own timeline for the identical period, and fewer than the downloaded CSV timesheet for the identical period. If that task is the ONLY work logged on a given day (no work_sessions row at all that day), the day is dropped from `days{}` entirely, so it also does not count toward activeDays/weekConsistency/avgPerDay/normCoverage/productivePct — a whole worked day can vanish from the period summary and the AI report while still fully appearing in DailyStatistics and the CSV export for the same range.

### [security] Every active user's Firestore read exposes every colleague's payRate (salary tiers) and other admin-only control fields — contradicts the project's own documented threat model

- **File:** `firestore.rules`:350-351  
- **Finder severity:** high  
- **Votes real:** 3/3

The /users/{userId} read rule is `allow read: if isAuthenticated() && (request.auth.uid == userId || isUserActive());`. Any authenticated, non-disabled worker (not just a manager/admin) can read the FULL document of any other user — there is no field-level restriction. That full document includes `payRate` (the NET hourly-rate tier table set by an admin, ADR 0012), plus `canBackdateTime`, `canEditOwnStartTime`, `isTest`, `teamManagerIds`/`overseerIds`/`seniorManagerIds`. This is not just a theoretical rules permissiveness: `src/context/UsersContext.jsx` (lines 30-45) does `onSnapshot(collection(db, 'users'), ...)` and spreads every field of every user doc (`{ id: doc.id, ...doc.data() }`) into app-wide React state (`users`/`usersMap`), and `UsersProvider` is mounted at the top of the whole app in `src/App.jsx` (line 77) above the single shared `/` route used by both workers and managers — so it runs for every logged-in user regardless of role, not just inside an admin-gated view. `UserManagement.jsx` (which is admin-only in the UI) simply reads `user.payRate` off this already-fetched, unfiltered array — but the underlying Firestore read that put `payRate` into every browser's memory happened before any role check, and is fully replayable by anyone with a valid session via the SDK/devtools regardless of which screens render.

This directly contradicts the project's own documented policy: `docs/security/threat-model-checklist.md` (lines 52-54, 101-106) explicitly lists `payRate` as a 'Read-restricted field' that 'must be checked — broad-read collections can still over-expose a sensitive field on the user doc,' and `docs/adr/0012-tiered-pay-rates-earnings.md` (line 51) states the intent as 'A worker can still read their OWN payRate' — not a colleague's. The actual rule was never scoped to enforce that: it only ever gated *writes* to payRate (`isAdmin() || payRate unchanged` on update, line ~434), never reads. Net effect: any worker can pull every teammate's negotiated salary tier and a handful of internal fraud-control flags out of a payroll/time-tracking app that explicitly intended those fields to be private.
